# Pods development

Pods is still in development. Read `docs/architecture.md` before you change how Pods talks to hosts, and `docs/roadmap.md` before you build a planned feature. The user documentation is in `docs/` (`manifest.md` for `pods.yml`, `proxy.md`, `ondemand.md`, `backups.md` and others), with front matter for foxws/laravel-docs (`title`, `section`, `order`, `tags`; the project's `metadata` on `docs/index.md`, where `kind: personal` lists Pods as a project rather than a Composer package), so link between pages as `page.md`. The README is a short overview that links to them.

## How Pods reaches a host

Page → Inertia controller in `src/Modules/Web` → action in `src/Domain/*/Actions` → `Integrations\Lpod\LpodClient` → `Integrations\Ssh\SshHostRunner` → `ssh` → `lpod … --json` on the host.

- Every environment is an SSH target, the local host too (`host.containers.internal`). Never add a code path that runs `podman`, `systemctl` or `journalctl` from Pods itself.
- Pods only runs lpod. If lpod lacks a command, it needs a PR in [foxws/lpod](https://github.com/foxws/lpod) first.
- **lpod version.** `config('services.pods.lpod_version')` (`PODS_LPOD_VERSION`) is the lpod release this Pods needs, and must equal `LPOD_REF` in `install.sh` (a test checks it); a release PR bumps both. `LpodVersionData::fromEnvironment()` compares it with the host's `facts['lpod']` (a release without `v`, or `dev-BRANCH`; a newer release isn't offered a downgrade). The host's settings page shows `LpodVersionCard.vue`, and `PUT environments/{environment}/lpod` (`EnvironmentLpodController`, `UpdateLpod`) runs `lpod self-update VERSION --json` through `LpodClient::selfUpdate()`, which only checks the exit code (lpod before 4.0.0-rc.2 prints text there), then `VerifyEnvironment`, and refuses with `CannotUpdateLpodException` when the host still reports another version. A feature that needs a newer lpod should also bump the pin.
- **Updating Pods.** `install.sh` writes `~/.local/bin/pods-update`, which runs the newest release's `install.sh` (GitHub's releases API, or `PODS_REF`) with its options. A rerun keeps the setup it finds (`keep_setup()`): the port (`installed_port()`), on demand when `lpod pods ondemand status` says so (`--idle` and `--no-idle` change it), and an installed `pods-proxy.container` with the host of Pods' main route, without rewriting the routes, which belong to Pods after the first install. A new install option should be read back from the host the same way, so `pods-update` needs no options.
- **Host facts.** `VerifyEnvironment` stores `lpod version --json` as the environment's `facts` (lpod, Podman and systemd versions, scope, user, hostname) and `last_seen_at`, which pages show instead of asking the host. It runs when a host is added, after Update lpod, daily through `pods:verify` (01:00, with `pods:sync`), and from Check again on `LpodVersionCard.vue` (`POST environments/{environment}/verification`, `EnvironmentVerificationController`, toast with the versions).
- Podman 6+ and systemd only. Don't add Docker or Podman Compose paths.
- Load the `quadlet` skill for how Quadlet keys, drop-ins and the systemd settings around them behave, before writing or suggesting unit content.

## Rules

- **Requests and passwords.** Forwarded headers count only from `config('essentials.trusted_proxies')` (private ranges; `SetTrustedProxies` applies it after boot, as `bootstrap/app.php` can't read `.env` or config), and `X-Forwarded-Host` never: behind the on-demand socket every client looks private, so don't rest a limit on the IP alone or put the request's host in a mail (`FortifyServiceProvider` builds reset links from `APP_URL`). A password change signs other sessions out (`authenticateSessions()`). A new route that checks the current password joins the `password-checks` limiter. A new password is `required` and `confirmed` in each Fortify action and in the setup request (`Password::default()` is neither), but not in `CreateUser`, which the command line shares. Password inputs are never trimmed.
- **Contract.** Every lpod payload carries `"contract": 1` (`LpodClient::Contract`). Fixtures in `tests/Fixtures/lpod/contract-1/` must match lpod's `tests/fixtures/contract-1/` byte for byte; copy them across instead of editing one side. Pods runs `vp check` over them, so format a new fixture with `pnpm exec vp check --fix` before it goes into the lpod PR.
- **Connections.** `SshHostRunner` reuses one SSH connection per host through a control master (`services.pods.ssh_control_persist`, 300 seconds, 0 turns it off; sockets in `ssh_control_directory`, outside the storage volume). Every unit that runs Pods (and so ssh) needs `RunInit=true`, since the masters are orphaned to PHP as PID 1; install.sh refuses a host without catatonit. Tests put the control directory in their temporary SSH directory (`tests/Pest.php`).
- **Arguments.** Pass lpod arguments as a list. `SshHostRunner` escapes each with `escapeshellarg` and wraps the command for fish/zsh login shells; don't build shell strings yourself.
- **Secrets.** Send secret values as the runner's `$input` (stdin). Never put them in arguments, props, logs, exceptions or the database. The same goes for passwords a setup step asks for. A request field that can carry one goes in `dontFlash()` (`bootstrap/app.php`), and a parameter that does gets `#[SensitiveParameter]`.
- **Caching.** Reads use `$this->cached($environment, 'key', [...])`, or `Cache::flexible` for slow Git reads (catalog, tags). Every write must `forget()` the keys it affects (often `host` too).
- **Timeouts.** Calls default to 30 seconds. Give prune, pull, install, exec (600) and stop-and-wait a longer timeout. Host calls that a page waits for run in the request (Octane's 90s limit is CPU time, not time waiting on SSH). Long jobs go to the queue instead: production runs `pods-queue.container` (`queue:work` on the database queue, whose `retry_after` must stay longer than the longest job), which isn't `PartOf=pods.container`: install.sh makes it an on-demand `--worker` with `pods:queue-idle` as the idle check, so it finishes a job while Pods sleeps.
- **Lifecycle.** Start, stop and restart use `--no-block`; the page polls for the result. Use `stopAndWait()` (blocking `APP down`) only when the next call starts units, so a start isn't merged into a pending stop.
- **Octane.** `RunsHostCommands` and `LpodClient` are scoped bindings. Don't keep host or request state in static properties or singletons.
- **Data.** Decode payloads into a spatie/laravel-data object with a `fromLpod()` method in the matching `src/Domain/*/DataObjects`, mark it `#[TypeScript]`, run `composer types:generate`, and re-export new types from `resources/js/types/index.d.ts`.
- **Routes.** Host pages go under `/environments/{environment}` in `routes/web.php`, actions in `routes/actions.php`. The settings sections (`SettingsController::Sections`) are at `/settings/{section}` and, with an environment selected, at `/environments/{environment}/settings/{section}` (`showInEnvironment`, which passes `environment` so the sidebar keeps its host); link to them with `settingsUrl(section)` from `useNavigation()`, never `SettingsController.show` directly. Use Wayfinder on the frontend, deferred props with skeletons for slow host data (give a slow one its own group).
- **Pressed buttons.** A button that stays on or off (Follow, Errors only) is a `UToggle` with `v-model`, and a pick-one row of them (the notifications filter) is a `UToggleGroup`, never a `UButton` with `:variant`, `:aria-pressed` and `@click`. Set `variant` and `active-color` instead of switching them yourself, and react to the model with a `watch`. In single mode, clicking the pressed item emits an empty value, so ignore that in the handler. Keep a `UToggleGroup` out of a `UFormField` that already holds an input: it clears the field's input id, so the label loses its input. That's why the schedule presets on the host's settings page stay buttons.
- **Props.** Read host data for a page with `ReadsFromHost::deferFromHost(fn () => …, 'group')` (or `optionalFromHost()` for polled data), which defers it and turns an `LpodException` into `{data: null, error}`. When a page's props need logic of their own (shared reads, memoized lookups), put them in a `ProvidesInertiaProperties` class in `Modules/Web/*/Props`, resolved from the container with its dependencies and given the page's subject with `for(...)`, so the controller only authorizes and renders (`ApplicationShowProps`, `ContainerShowProps`). The props stay the same, so the feature tests don't change.
- **Live props.** `LpodClient::forget()` also broadcasts `Domain\Environments\Events\EnvironmentChanged` (`ShouldBroadcastNow`, no payload, private channel `environments.{ulid}` authorized by `Modules\Api\Environments\Broadcasting\EnvironmentChannel`, as `environment.changed`), deferred once per request and host, `dontBroadcastToCurrentUser()`, inside `rescue()` so an unreachable Reverb never fails a write. Pass `live: $environment` to `deferFromHost()`/`optionalFromHost()` for props that show host state (lists, status, details); leave logs, stats, the journal, the catalog, updates and create-page form data without it. Pages keep polling (`useHostReload`, `useHostPolling`), since Pods doesn't see changes made outside it: `useHostPolling` reloads every 5 seconds while busy (or every `refresher` seconds when that is shorter) and otherwise every `refresher` seconds (shared prop from `GeneralSettings::$host_refresh`, choices in `GeneralSettings::HostRefreshChoices`, 10 by default, reads cached for `PODS_CACHE_TTL` so a 3-second poll mostly hits the cache; 0 pauses the idle poll but keeps the busy one), and its third argument names props only reloaded while busy (the application page's `logs`). Every poll is one SSH login per uncached prop, so keep idle polls slow and small. Production runs Reverb as `pods-reverb.container` (`PartOf=pods.container`, same image, `reverb:start` on 8080); `config('octane.caddy.env')` forwards `/app/*` to `OCTANE_REVERB_UPSTREAM`, and an empty `VITE_REVERB_HOST` makes Echo use the page's own address (`resources/js/plugins/echo`). A tab hidden for a minute disconnects Pusher (not Echo's `connect()`, which drops the channels) so an on-demand Pods can sleep. install.sh writes the Reverb settings into a new `pods-env`, and `add_reverb_env` adds them once to an older one. Test with `Event::fake([EnvironmentChanged::class])`; deferred props name their `liveProps` listeners only in the partial reload that loads them.
- **Lists.** Host lists sort in the browser: give `DataTable` a `sortable` list of `SortableColumn`s (`resources/js/utils/sorting.ts`; `column` is the column id, `value` what it sorts on, `descendingFirst` for CPU, memory, size and dates, `timeOf()` for timestamps). Headers become `SortableHeader` buttons (first direction, the other, none), and phones, which show the `item` cards, get `TableSortControls` with the same state. A page with its own `UTable` uses `useTableSort()` and the `#COLUMN-header` slots (ApplicationIndex, SecretIndex). Rows without a value go last in both directions, and the sort survives polls and live updates.
- **Errors.** Let `LpodException` surface as a toast (`toast()` in `src/Foundation/Helpers.php`, or `WritesToHost::toHost()`); check how sibling controllers do it. A refusal Pods decides itself before touching the host gets its own domain exception (such as `CannotUpdateApplicationException`).

## Adding a host feature

1. lpod: add the `--json` command and its fixture (see the lpod repo; it has no test suite, so check it with `shellcheck` and stubbed `podman`/`systemctl`/`git` on the PATH, and say it still needs a real-host check). Document it in lpod's `docs/commands.md`.
2. Copy the fixture to `tests/Fixtures/lpod/contract-1/` and add its pattern to `fakeLpod()` in `tests/Pest.php` (more specific patterns first).
3. Add the `LpodClient` method, the data object and the cache keys.
4. Add the action, the controller, the route and the Vue component, following the sibling module.
5. Write feature tests with `fakeLpod()`: assert the props, the exact arguments with `$lpod->assertRan([...])`, stdin for secrets, the order of calls when it matters (`collect($lpod->recorded())->pluck('arguments')->search(...)`), and the error toast when lpod fails (`$lpod->respond('pattern', new HostResult(1, '', 'message'))`). Run `vendor/bin/pest tests/Feature tests/Unit`; the Browser tests hang here.
6. Update `docs/roadmap.md`, the page in `docs/` that describes it (and the README's feature list), or `docs/architecture.md`, and this skill.

## pods.yml (ManifestData)

Every request that takes a repository URL uses `FetchQuadletsRequest::repositoryRules()` and `repositoryMessages()`, which also refuse credentials in it. Catalog repositories are `CatalogSettings` (Settings, Catalog; `CatalogSettingsController`, admins only), seeded with foxws/quadlets by a settings migration. `config('catalog')` only has the release-pinned proxy source. They're third-party input: `ListCatalog` shares one time budget between them and puts a repository it can't read in `CatalogData::$failures` (it only throws when all fail), so a bad one doesn't hide the others. Key catalog entries by repository and path, since names repeat.

`Domain\Quadlets\DataObjects\ManifestData::fromYaml($yaml, $directory)` parses and validates it; invalid manifests throw `InvalidManifestException` and are ignored (shown as `manifest_error`). Keys:

- Catalog metadata (`name`, `label`, `description`, `author`, `icon`, `category`, `website`, `repository`, `notes`) and `sources` (paths relative to the manifest's directory).
- `secrets`: how to ask for each, `generate`, or `from` + `key` of a `format: dotenv` secret (resolved on the server).
- `after_install` and `after_update`: setup steps (`ManifestSetupStepData`, `ManifestData::setupStep($name)` finds one in either list; a name can't be in both): a Quadlet `container`, `user`, `workdir`, a whitespace-split `command`, and `inputs`. An input with `option` goes in as one `--option=VALUE` argument (so a value starting with `-` can't pass as a flag); at most one input has no option and goes on stdin, and a password always does.
- `ondemand`: the keys of lpod's ondemand status, parsed with `OnDemandSettingsData::fromLpod()` and validated with its shared patterns.
- `routes`: role → `upstream` (`CONTAINER:PORT`), `description` and `main` (`ManifestRouteData`); the first is the main one unless another says `main: true`. Hostnames are never in pods.yml.
- `timers`: name → `description`, `container`, `on_calendar` (a string or a list, kept as a list), `persistent`, `randomized_delay_sec`, `timeout_start_sec` (`ManifestTimerData`, `forLpod()`). The keys are the systemd directives in snake_case. Names follow `ManifestTimerData::NamePattern`, and `idle` is refused (on-demand's `APP-idle.timer`). A container has at most one timer.

## Installations

`Domain\Applications\Models\Installation` keeps, per environment and application, the Git source (repository, reference, path, commit), the raw pods.yml (parsed on read, so new keys need no migration), a sha256 checksum per file, the files changed outside Pods, and how each setup step ended (`setup`, never its inputs). `SyncInstallation` compares with `lpod APP files --json` on the application page and in `pods:sync` (daily, 01:00 UTC), ignoring lpod's own drop-ins (`*.d/lpod-*.conf`) and local ones (`*.d/*.local.conf`, `SyncInstallation::LocalDropInPattern`); `SyncInstallation::isTracked()` decides both, and `UpdateApplication` never lists or removes either. Inside the model, read the column with `getAttribute('changes')`: `$this->changes` is Eloquent's own list of attributes the last save changed.

- **Adopting:** `AcceptInstalledFiles` ("Keep these files" / "Track these files") takes the host's files as they are, without a source. `LinkApplicationSource` (`PUT applications/{app}/source`, `ApplicationSourceController`, validated by `FetchQuadletsRequest`, UI `ApplicationSourceModal.vue`) fetches a repository, reference and path for an application installed outside Pods, and keeps the source with the *source's* checksums (keeping `setup` and `installed_at`), then syncs, so the files that differ show as changed outside Pods. While an installation has changes, `ApplicationUpdateController` also accepts its own reference as the tag ("Replace with REF" on the Source card); `UpdateApplication` then keeps `updated_from` when the fetched commit is the stored one, so a replace doesn't ask for `after_update` steps.

## Built features to follow

- **Drop-ins:** lpod's `APP files write NAME --stdin --json` (lpod #52) writes `QUADLET.d/FILE.conf` next to one of the app's Quadlets (content on stdin, 256 KiB at most, `lpod-*.conf` and symlinks refused, `daemon-reload`) and answers `{file: {name, path, content}}`; `APP files remove` removes one. `LpodClient::writeFile()` throws `unsupportedCommand` when the reply has no `file` (an older lpod lists the files instead). `PUT`/`DELETE applications/{app}/drop-ins` (`ApplicationDropInController`, `WriteDropInRequest`/`DropInRequest` with `DropInRequest::NamePattern`, `restart` optional, the route excluded from `trimStrings` like the Quadlet routes) run `WriteDropIn`/`RemoveDropIn`, which update the installation through `TrackInstallation::edited()`/`removed()` (a tracked drop-in gets or loses its checksum; a local one is never tracked), then restart with a toast of their own, so a failed restart doesn't say the file wasn't saved. UI: `ApplicationFilesTab.vue` (the Quadlet files tab of the application page, with `QuadletEditModal.vue` for Quadlets, which sends `restart` with an `edit` install so `QuadletController` restarts on the server), `ApplicationDropInModal.vue` (new drop-ins are always `NAME.local.conf`, `localDropInName()` in `utils/quadlet.ts`), lpod's own shown read-only.
- **Drop-in patterns** live in PHP (`SyncInstallation`, `DropInRequest::NamePattern`) and TypeScript (`utils/quadlet.ts`), so keep both in step, like `utils/routes.ts`. What's still open is in `docs/roadmap.md`, Drop-ins.
- **Setup steps:** `ApplicationSetupController` runs a step of `after_install` or `after_update` with `RunSetupStep`, which resolves the step's Quadlet to the Podman container name through `lpod containers`, runs `lpod container NAME exec [--stdin] --json -- …`, records the exit code, and flashes the output once (`Inertia::flash('setup', …)`). UI: `ApplicationSetupCard.vue`, which shows the `after_update` steps once the installation has an `updated_from`, and counts one as done only when it ran since `installed_at`.
- **On-demand:** `lpod APP ondemand enable|disable|status`. The dialog is filled from the stored manifest's `ondemand:` when it has one (`OnDemandSuggestionData::from_manifest`), or else from the Quadlet files (`SuggestOnDemandSettings`). `listen` must be in the request (null is every address, so never drop it), and is suggested from pods.yml or else the main unit's `PublishPort=`. A sleeping app's Start is Wake: lpod's `up` starts `APP-ondemand.service` instead of the `StopWhenUnneeded=yes` main unit.
- **Timers:** lpod's `APP timers [set --stdin|remove|run NAME] --json` writes `APP-NAME.timer` (`Unit=` the container's service, `[Install] WantedBy=timers.target`, settings on its `# lpod-timer:` line) and a `lpod-timer.conf` drop-in for `timeout_start_sec`. `ApplyManifestTimers` sets the stored manifest's timers after `QuadletController` installs (its own error toast; the install still counts) and inside `UpdateApplication` (a failure becomes `timers_error` in the update toast). It only asks the host when the new or the previous pods.yml names timers, and the page's `timers` prop (group `details`, `LpodClient::timers()`, cached as `apps.APP.timers`) is `[]` without asking when the stored pods.yml has none, so hosts whose lpod lacks `timers` keep working. `ApplicationTimersCard.vue` shows them with Run now (`POST applications/{app}/timers/{timer}/run`, `ApplicationTimerController`). A Laravel scheduler stays `ondemand.schedule`: it replaces `schedule:work` only while on demand, so as a timer it would run tasks twice.
- **Updates:** `ListApplicationUpdates` offers the newer tags of the stored repository (`lpod quadlet tags`, `version_compare`, pre-releases only after a pre-release). An installation at a branch gets that branch as its one update (`GitTagData` with the branch's name and short commit) when `lpod quadlet head` (`LpodClient::branchHead()`, cached for two minutes) gives a commit the stored short one doesn't start. The update request's `tag` is then the branch, and the Source card tells a branch update by its name matching the installed reference. `UpdateApplication` fetches the tag, runs `quadlet check` (a failure says when Pods last saw an older lpod on the host than it needs, through `LpodVersionData`, since lpod before 4.0.0-rc.3 counted the generator's log lines as errors), refuses missing secrets, then stops and waits, removes the files Pods installed that the tag no longer has (`lpod APP files remove`), and installs with `--replace --start`. Then it keeps the reference it came from (a branch's old commit) as `updated_from`, which a fresh install clears (`TrackInstallation`), and the toast names the new release's `after_update` steps.

## Proxy routes

lpod generates each application's routes file, with the routes kept on its `# lpod-routes:` line. It writes `sites/APP.Caddyfile` with a site per hostname, or, when the proxy's Caddyfile imports `sites/*.caddy` inside a wildcard site, `sites/APP.caddy` with matchers and `handle`s (`proxy.layout` is `handlers`, and `proxy.domain` is the wildcard domain). It also writes a `pods-proxy.container.d/lpod-routes-APP.conf` drop-in with the app's networks, from `lpod APP routes set --stdin --json` (`{"routes": [{role, host, upstream, main}]}`). An empty list removes them, and it reloads Caddy or restarts the proxy when the networks change. While an app is on demand, its main route targets its socket (`host.containers.internal:PORT`, reported as `target`), unless the socket only listens on a loopback address (`--listen 127.0.0.1`), which the proxy container can't reach: then it goes to the container, so it only works while the app is awake (lpod #48). Pods reads `lpod proxy routes --json` (`LpodClient::proxyRoutes()`, cached as `proxy.routes`) for `ProxyRoutesData`, and writes with `setRoutes()`.

- `RouteData` holds the patterns (role, host, upstream), `rules($key)` and `forLpod()` (lowercase hosts, one main route, and `via` dropped from the main route). Use them for any request that takes routes. A route with `via: main` goes where the main route goes and shares its matcher, for apps that route their own hostnames (a Laravel app whose own Caddy forwards to Reverb). Every `reverse_proxy` gets `stream_close_delay 5m`, and reloads go through `admin unix//…` when the Caddyfile has it.
- `SuggestRoutes` merges an app's routes with the ones its stored pods.yml names, and suggests `APP.home.arpa` for the main one and `ROLE.APP.home.arpa` for the others, or `APP.DOMAIN` and `APP-ROLE.DOMAIN` behind a wildcard site (one label, so its certificate covers them). The install page gets a deferred `proxy` prop for that. `resources/js/utils/routes.ts` mirrors that suggestion, so keep both in step.
- The application page has a deferred `routes` prop (group `routes`) for `ApplicationRoutesCard.vue` and `ApplicationRoutesModal.vue`, and `PUT applications/{app}/routes` saves them (`ApplicationRoutesController`). The install page sends `routes` with the install, and `QuadletController` sets them afterwards. If that fails, the install still succeeds and the toast says so.
- Inside a `v-for`, Nuxt UI's `ULink` made vue-tsc lose the loop variable, so `ApplicationRoutesCard.vue` uses a plain `<a>`.

### Proxy settings

- `lpod proxy settings [set --stdin] --json` (`LpodClient::proxySettings()`, cached as `proxy.settings`, and `updateProxySettings()`, which forgets `proxy.settings`, `proxy.routes` and `secrets`) reads and writes the mode (`ProxySettingsData::Modes`: `letsencrypt`, `local`, `wildcard`, `http`), email, wildcard domain, DNS provider (`DnsProviders`, Cloudflare only, the plugin in `ghcr.io/foxws/pods-proxy`), resolvers, ports and image. lpod keeps them on the Caddyfile's `# lpod-proxy:` line and in `pods-proxy.container.d/lpod-proxy.conf`. `managed: false` means a hand-written Caddyfile, read as far as lpod can, that saving backs up (`backup` in the reply) and replaces.
- The DNS token goes in the settings JSON on stdin (`dns_token`), into the Podman secret `pods-proxy-dns-token`; leave it out to keep the one on the host. It's never in arguments, props or the database.
- `ProxySettingsRequest` validates both the install and the save, and drops what the mode doesn't use (`exclude_unless:mode,wildcard`, no HTTPS port in `http`).
- `EnvironmentProxyController`: `POST environments/{environment}/proxy` runs `InstallProxy` (fetch `config('catalog.proxy')`, Pods' own `containers/proxy`, and install it as `pods-proxy` through `InstallQuadlets` without starting it, so the `Installation` keeps its source), then saves the settings, then `up`, so the first start has the right ports. `PUT` saves them, and `GET …/proxy/certificate` downloads `lpod proxy certificate --json` as a `.crt`. Removing the proxy is the application's remove.
- UI: `ProxySettingsCard.vue` on the host's settings page (deferred `proxy` prop, group `proxy`). It warns when rootless Podman can't publish the ports (`unprivileged_port_start`). The certificate button is a `UButton` with `external`, so it's a plain download, not an Inertia visit.
- `ghcr.io/foxws/pods-proxy:main` is Caddy built with xcaddy (`containers/runtimes/proxy/Containerfile`, published by `.github/workflows/build-proxy.yml` on changes and weekly). A new DNS provider needs another `--with` line there, its name in `ProxySettingsData::DnsProviders`, and its token variable in lpod's `proxy_dns_env`.
- `install.sh --proxy` calls `lpod proxy settings set` only while there's no Caddyfile yet, so running it again keeps settings made in Pods.
- `install.sh` lets Pods sleep behind the proxy too: with `--proxy`, or whenever `lpod pods routes` has a route, `enable_idle` leaves out `--listen 127.0.0.1` (`IDLE_LISTEN`), so the socket listens on every address, lpod points the route at `host.containers.internal:PORT`, and install.sh warns to block the port in the firewall. The proxy container can't reach the host's 127.0.0.1; a unix socket fails under SELinux (`container_t` can't connect to the user systemd's `unconfined_t` socket, even relabeled), and user socket units ignore `IPAddressAllow=`/`IPAddressDeny=` (both checked on a real host). Pods listens on 127.0.0.1:9393 by default (Cockpit has 9090); `--port` writes `pods.container.d/install-port.conf` (resetting `PublishPort=`), and a rerun keeps the installed port (the on-demand socket's, else the unit's last `PublishPort=`). It installs lpod through lpod's own installer at `LPOD_REF` (a raw `bin/lpod` reports `dev`), and upgrades an older release or a plain `dev` copy, keeping a git checkout or a `dev-BRANCH` build.
- `install.sh --no-pods [--authorized-key KEY]` only prepares a host or user for a Pods elsewhere: the requirement checks, lpod, and the key in `authorized_keys` (`authorize_key`, shared with the local install). It refuses `--proxy`, `--host`, `--uninstall` and the owner options, since that Pods installs the proxy and keeps its source.
- The fields (mode, domain, token, email, and under Advanced the DNS provider, resolvers, ports and image) are `ProxySettingsFields.vue`, shared by the host's card and the defaults form, with `ProxySettingsFormValues` from `resources/js/types/index.d.ts`.

### Proxy defaults

- `Foundation\Settings\ProxySettings` (spatie/laravel-settings, group `proxy`, migration in `database/settings`): mode, email, domain, DNS provider, resolvers, ports and image. Never the DNS token: that's only ever on the host. Settings, Proxy (`SettingsProxyForm.vue`, super-admin) reads and saves them through `ProxyDefaultsController` (`actions/settings/proxy`, JSON `show` like `ApplicationSettingsController`), validated by `ProxyDefaultsRequest`, which authorizes `manage-application-settings` itself so a regular user gets a 403 rather than validation errors.
- The host settings page gets them as `proxyDefaults`, and `ProxySettingsCard.vue` starts from them while the proxy isn't installed (the domain only in the wildcard mode). An installed proxy always shows what lpod reads from its host.
- Their domain is what `SuggestRoutes` (which gets `ProxySettings` injected) suggests under instead of `home.arpa` outside a wildcard site: `ApplicationRoutesData::$default_domain` for the Routes modal, and the create page's `defaultDomain` prop. `suggestedHost()` in PHP and `utils/routes.ts` both take it as their last argument.
- Pods' own hostname: `install.sh --proxy --host NAME` runs `lpod pods routes set` (role `app`, `systemd-pods:8000`) and removes the older `sites/pods.Caddyfile` and `pods.conf` drop-in, so it's edited on the `pods` application's Routes card. While Pods is on demand, lpod sends that route to its socket (see install.sh above).
- Still open (docs/roadmap.md, Proxy): waking sleeping services on routes that aren't `via: main`.

## Volume exports

- lpod's `volume export NAME [--stop] --json` writes the tar archive (`podman volume export`) to stdout, not JSON. It refuses volumes with a `device` option (`lpod volumes` reports bind-backed ones as type `device`, with the folder as `mountpoint`) and NFS. `--stop` stops the applications whose running containers use the volume and starts them again afterwards, also on failure (an `EXIT` trap).
- **Sizes.** `lpod volumes --json` always has `size: null`, since sizes walk every file. `lpod volumes sizes --json` (lpod #51) gives `{name, size}` for named and anonymous volumes (`du` through `podman unshare`); `LpodClient::volumeSizes()` maps it by name, cached as `volumes.sizes` for 10 minutes (`Cache::flexible` [600, 3600]), timeout 300, never forgotten by writes, and `[]` from an older lpod (which answers with the plain volume list). The Volumes page has it as the deferred group `sizes`, neither live nor polled, merged into the rows by name with `useVolumeSizes()` (`sizeOf()`, `isSizing()`), with a skeleton while it loads. Which volumes Podman stores itself (named, anonymous), and so can be exported and measured, is `isInPodmanStorage()` in `resources/js/utils/volumes.ts`, mirroring `HostVolumeData::isExportable()`.
- `RunsHostCommands::download()` streams a command's stdout into a file: `SshHostRunner` runs ssh through the shell with `> PATH`, so the archive never passes through PHP; `FakeHostRunner` writes the response's output there (`fakeLpod()` answers `volume export *` with a string). `LpodClient::exportVolume()` checks the result like any call (`verify()`).
- `Domain\Volumes\Models\VolumeExport` (status `VolumeExportStatus`, `stop_applications`, `path` on the `backups` disk, `storage/app/backups/ENV/VOLUME/ULID.tar`, `size`, `error`) is the only record of an export; deleting one deletes its archive. `QueueVolumeExports` creates one per volume (skipping volumes with one waiting or running) and dispatches `Jobs\ExportVolume` for each: `tries` 1, a timeout of `services.pods.volume_export_timeout` (3600) plus 60, an `LpodException` is an outcome (`failed()`, no retry), and `failed()` also deletes a partial archive. It notifies the user with `VolumeExportFinished` (`database`, then `broadcast` with `onConnection('sync')`, type `volume-export.finished`, inside `rescue()`), which `useVolumeExportNotifications()` in `DashboardLayout.vue` shows as a toast with the download link; the stored row links to the Volumes page (see Notifications).
- `VolumeExportController` (`actions/environments/{environment}/volume-exports`, scoped bindings): `store` takes `volumes` or `application` (its volumes where `HostVolumeData::isExportable()`, named or anonymous) and `stop_applications`; `download` only needs a signed link (`VolumeExportData::downloadUrl()`, a day), so it works from a notification; `destroy` refuses an unfinished export (409). The Volumes page gets `exports` (the newest 25, from the database, not the host), shows them in `VolumeExportsCard.vue`, polls them every 5 seconds while one is unfinished, and starts exports with `VolumeExportModal.vue`.
- `pods:prune-exports` (daily, 01:00) keeps `services.pods.volume_exports_kept` (3) finished archives per volume, removes failed exports after a week, fails exports unfinished after twice the timeout, and removes the folders of removed hosts.
- Not built yet: restores (`lpod volume import`), see `docs/roadmap.md`. Ask the user before adding a dependency or a new disk.

## Notifications

- Notifications that should outlast the toast use the `database` channel before `broadcast` (so the row exists when the broadcast reloads pages), with a `toDatabase()` of `title`, `message`, `level` (`Domain\Users\Enums\NotificationLevel`), `url` (a relative path, `route(..., absolute: false)`, never a signed link that expires) and `environment` (the host's name). `toArray()` stays the broadcast payload. `NotificationData::fromModel()` reads that shape, falling back to the class name and `info`.
- `NotificationController` (`Modules/Web/Notifications`): `GET /notifications` and `GET /environments/{environment}/notifications` (`environment`, so the sidebar keeps its host; link with `notificationsLink` from `useNavigation()`) render `Notifications/NotificationIndex` with `filter` (`all`, `unread`) and `messages` (`Inertia::scroll`, 25 a page, `InfiniteScroll`). `PUT`/`DELETE actions/notifications/{id}` mark one read (`read: bool`) or remove it, through `$user->notifications()` so only the user's own; `NotificationBulkController` `PUT`/`DELETE actions/notifications` marks all read and clears the read ones.
- The shared `notifications` prop is the unread count, for `NotificationBell.vue` in `AppNavbar.vue`. `useNotificationUpdates()` in `DashboardLayout.vue` reloads it (and `messages` on the page) on every broadcast notification on `users.{id}`.

## PWA

Pods is installable through foxws/laravel-pwa (`config/pwa.php`, `@pwaHead` and `@pwaSw` in `resources/views/app.blade.php`, `public/offline.html`). The production entrypoint runs `pwa:generate` for the web server only. The icons and the manifest's screenshots are in `public/images/`, not `storage/app/public` as the package suggests: `pods-data.volume` is mounted over `/app/storage`, so files there never reach an existing install. `tests/Feature/Support/PwaTest.php` checks that every path in the config is a file in `public/`. The logo is the AppLogo badge (`--logo-gradient` with Lucide's `box`), and the screenshots also live in `francoism90/.github` under `assets/pods`.

## Runtime images

Pods builds its own images from `docker.io/dunglas/frankenphp:1-php${PHP_VERSION}-trixie` (Debian, glibc; `PHP_VERSION` build arg, 8.6 by default), not from a shared Laravel base image. `containers/runtimes/production/Containerfile` has a `base` stage (openssh-client, gosu, `bcmath intl mbstring opcache pcntl`, `setcap -r` on frankenphp for `--cap-drop=all`, the `docker` user 1000:1000), a `build` stage (Node and npm copied from `node:${NODE_VERSION}-trixie-slim`, pnpm, Composer; runs `composer install --no-dev`, `octane:install` and `pnpm build`, then drops `node_modules` and `.env`) and the `production` stage CI builds (`--target=production`), which copies `/app` from `build` and ships no Node, Composer or pnpm. SSR is off (`config/inertia.php` defaults `INERTIA_SSR_ENABLED` to false): no SSR server runs, and `pnpm build` makes the client bundle only. Both images set `HEALTHCHECK NONE`, since the official image's check polls Caddy's admin port, which the queue, Reverb and scheduler containers don't serve. `containers/runtimes/development/Containerfile` has a `development` stage (what `pods-dev.build` builds) with the same base plus Xdebug, redis (Valkey), Composer, Node, pnpm and Playwright's OS deps, and the host's UID/GID from `pods-dev.build`. Its `devcontainer` stage adds Git, gh, Claude Code, Codex and Laravel LSP for `containers/devcontainer/devcontainer.json` (VS Code Dev Containers; `ENTRYPOINT []`, so Octane doesn't start; `--add-host=host.containers.internal:host-gateway` and `--init` like `pods-dev.container`). `.github/workflows/build.yml` rebuilds the latest stable release (`gh release view`, or the newest pre-release while there is none) every Monday (and from `workflow_dispatch` with `rebuild-release`) under its own tags, without the layer cache and with `--pull=always`, so `AutoUpdate=registry` in the units picks up Debian and PHP security updates between releases. A new PHP extension goes in `install-php-extensions` in both files. Check `composer check-platform-reqs --no-dev` first, and keep in mind that the official image builds PHP without mbstring, which a polyfill only partly replaces.
